# 행정규칙 수집 + 색인 설계

- 날짜: 2026-06-03
- 상태: 승인 대기(스펙 리뷰)
- 대상 저장소: `search/` (seongilp/fast-law-search), 데이터는 `../kr/`

## 1. 목적 / 배경

현재 검색 시스템은 `kr/**/*.md`(법률·시행령·시행규칙·대통령령 등)를 조문 단위로 Typesense에
색인해 빠른 본문 검색을 제공한다. 행정규칙(전자금융감독규정 등 고시·훈령·예규·세칙)은 법령
API와 별도 엔드포인트(`target=admrul`)라 현재 수집되지 않아 검색되지 않는다.

목표: law.go.kr OpenAPI에서 **현행 행정규칙 전체(약 24,052건)**를 수집해 기존 법령과 **동일한
조문 단위 검색 경험**(본문 전문검색 + 패싯 + 랭킹)을 제공한다.

## 2. 핵심 결정

| 결정 | 선택 | 근거 |
|---|---|---|
| 저장 위치 | **`kr/` 안에 직접 저장** | 인덱서가 이미 `kr/` 전체를 글로빙 → 인덱서 변경 0 |
| upstream | **push 하지 않음** | `kr/`는 upstream `legalize-kr` 미러지만, 행정규칙은 로컬에만 보관 |
| 검색 방식 | 수집 + 색인 (실시간 호출 아님) | 조문 단위·고속·정부 API 가동률 비의존, 법령과 동일 UX |
| 수집 범위 | **현행(現行)만** | 검색 대상과 일치, 24,052건. 연혁(이력)은 v2 |
| 별표/부칙 | v1은 frontmatter 메모 수준, 본문은 조문 위주 | 검색 가치 우선, 별표 PDF 링크는 메타 보존 |

## 3. API 계약 (검증 완료)

OC 키: `lawmcp123` (law.go.kr 사용자 ID, `.env`로 주입 — 하드코딩 금지)

### 3.1 목록 조회

```
GET https://www.law.go.kr/DRF/lawSearch.do
  ?OC={key}&target=admrul&type=json&display=100&page={N}
```

- `display` 최대 100, `totalCnt=24052` → **241페이지**
- 응답 `AdmRulSearch.admrul[]` 각 항목 필드:
  `행정규칙명`, `행정규칙종류`(고시/훈령/예규/세칙/규정/지침…), `소관부처명`,
  `발령일자`, `시행일자`, `발령번호`, `행정규칙ID`, `행정규칙일련번호`(MST), `현행연혁구분`
- 단건만 있으면 `admrul`이 list가 아닌 dict로 올 수 있음 → 정규화 필요

### 3.2 본문 조회

```
GET https://www.law.go.kr/DRF/lawService.do
  ?OC={key}&target=admrul&type=json&LID={행정규칙ID}
```

- **반드시 `LID`(=행정규칙ID)** 사용. `ID`/`MST`는 "일치하는 행정규칙이 없습니다" 오류.
- 응답 `AdmRulService` 구조:
  - `행정규칙기본정보`: 행정규칙명·발령일자·시행일자·행정규칙종류·소관부처명·발령번호·
    행정규칙ID·행정규칙일련번호·현행여부·조문형식여부
  - `조문내용`: **문자열 리스트**. 항목은 두 종류:
    - 조문: `"제1조(목적) 이 규정은 …"`  (조문 헤더 + 본문이 한 문자열)
    - 구조 헤더: `"제1장 총칙"`, `"제2장 …"`
  - `별표`: `별표단위[]` (별표제목, 별표번호, 별표서식PDF파일링크, 별표내용)
  - `부칙`: `부칙공포일자`, `부칙공포번호`, `부칙내용`
  - `제개정이유`, `첨부파일`
- 오류 응답: `{"Law": "일치하는 행정규칙이 없습니다. …"}` (정상 응답은 `AdmRulService` 키)

## 4. 컴포넌트 (모두 `search/` 내부)

```
search/
  collector/                     # 신규
    __init__.py
    config.py    # OC 키, ADMRULE_ROOT(기본 ../kr), 동시성·throttle 설정 (.env)
    client.py    # API 클라이언트: list_rules(), fetch_body(rule_id) — throttle+retry
    convert.py   # 순수함수: admrul JSON → (frontmatter dict, markdown 본문)
    write.py     # 파일 경로 결정(충돌 해소) + 원자적 쓰기
    fetch.py     # 오케스트레이션 CLI: 목록 페이징 → 본문 → 변환 → 저장 (resume)
    requirements.txt
  indexer/        # 변경 없음 (kr/ 글로빙 그대로)
```

각 모듈 단일 책임 / 순수함수 우선:
- `client.py`: I/O만. 네트워크·재시도. 파싱은 호출측.
- `convert.py`: **순수함수**(네트워크/파일 없음). 입력 JSON dict → 출력 (meta, body). 단위 테스트 용이.
- `write.py`: 파일시스템만. 경로 충돌 규칙 적용.
- `fetch.py`: 조립 + 진행률 + resume 판단.

## 5. 데이터 변환 규칙 (`convert.py`)

### 5.1 Frontmatter (법령 포맷과 동일 키)

```yaml
---
제목: 전자금융감독규정
법령MST: 2100000274812        # 행정규칙일련번호
법령ID: "21828"               # 행정규칙ID
법령구분: 고시                 # 행정규칙종류 → law_type 패싯
소관부처:
  - 금융위원회
공포일자: 2026-02-13          # 발령일자
공포번호: "2026-7"            # 발령번호
시행일자: 2026-02-13
상태: 시행                    # 현행여부 Y → 시행
출처: https://www.law.go.kr/행정규칙/전자금융감독규정
데이터구분: 행정규칙           # 법령과 구분하는 표식
별표: []                      # 별표 메타(제목+PDF링크) 보존
---
```

- `제목` Unicode 정규화: 가운뎃점 `·`(U+00B7) → `ㆍ`(U+318D) — 기존 규칙과 동일
- `발령일자`가 Unix epoch 이전이면 git 커밋 날짜 이슈는 v1 범위 밖(파일 frontmatter엔 정확히 기록)

### 5.2 본문 (조문 마크다운)

`조문내용` 리스트를 순회하며:
- `제N장|제N편|제N절|제N관 …` → `## {그대로}` (구조 헤더, 기존 파서 `_STRUCT_RE`와 호환)
- `제N조(제목) 본문…` → `##### 제N조 (제목)` 줄 + 다음 줄부터 본문
  - 정규식으로 `제N조(의M)?` + `(제목)` 분리. 기존 파서 `_ARTICLE_RE`가 읽는 형식과 일치시킨다.
  - 본문 안의 항(①②)·호(1.2.)는 v1에선 원문 그대로 둔다(검색에는 충분). 가독성 향상은 v2.
- 첫 문서 제목으로 `# {행정규칙명}` 1줄 추가(기존 법령 md와 동일)
- 부칙: 본문 끝에 `## 부칙` + `부칙내용` 추가(있을 때)

## 6. 파일 경로 / 충돌 해소 (`write.py`)

- 기본: `kr/{행정규칙명(공백 제거, 정규화)}/{행정규칙종류}.md`
  - 예: `kr/전자금융감독규정/고시.md`, `kr/전자금융감독규정시행세칙/세칙.md`
- 충돌 규칙(기존 README 규칙 준용):
  - 같은 경로를 다른 `행정규칙ID`가 이미 사용 → `{종류}({행정규칙ID}).md`
  - 기존 법령 디렉터리와 이름이 겹치면 행정규칙 파일은 종류 기반 파일명으로 공존
- 쓰기는 임시파일 → rename(원자적). 부분 파일 방지.

## 7. 안정성 / 멱등성 (`fetch.py`)

- **Throttle + 동시성 제한**: 기본 동시 6, 요청 간 최소 간격. 지수 백오프 retry(429/5xx/타임아웃).
- **Resume**: 대상 파일이 이미 있고 frontmatter `법령MST`(행정규칙일련번호)가 같으면 스킵.
  → 중단 후 재실행 안전, 주기 갱신 시 변경분만 다시 받음.
- **파일 단위 격리**: 한 건 실패가 전체 중단을 막지 않음. 실패 목록은 stderr + 요약 카운트.
- 진행률: 200건마다 `[progress] i/24052` 형식(기존 인덱서 톤과 일치).

## 8. 설정 (.env, 하드코딩 금지)

```
LAW_GO_KR_OC=lawmcp123
ADMRULE_ROOT=../kr           # 행정규칙 markdown 저장 루트 (= 법령과 동일)
COLLECT_CONCURRENCY=6
COLLECT_RETRY=3
```

`config.py`는 `dataclass(frozen=True)` 불변 설정 객체로 `.env`에서 로드(기존 indexer/config.py 패턴 동일).

## 9. 실행 흐름 (Makefile 타깃 추가)

```
make collect      # python collector/fetch.py  → kr/ 에 행정규칙 md 생성/갱신
make index        # (기존) kr/ 전량 재색인 → 법령+행정규칙 통합 검색
```

수집 → 색인 2단계. v1은 수동 실행. 주기 갱신(GitHub Action/cron)은 v2.

## 10. 테스트 전략

- `convert.py` **순수함수 단위 테스트**(pytest): 실제 전자금융감독규정 JSON 픽스처(`/tmp/admrul.json` 기반 축약본) → 기대 frontmatter/조문 마크다운. 조문/구조헤더/부칙/단건 dict 정규화 케이스.
- `write.py` 경로 충돌 해소 단위 테스트(임시 디렉터리).
- 통합 스모크: 1~2건 실제 수집 → 파일 생성 → 기존 `parse_file`로 재파싱해 조문 추출되는지 검증(파서 호환성 보장).
- 색인 검증: `make index` 후 "전산실" 등 본문 단어로 행정규칙 조문이 검색되는지 확인.

## 11. 범위 밖 (v2 후보)

- 연혁(이력) 행정규칙 수집
- 항/호 마크다운 정형화(`**①**` 등)
- 별표 본문 텍스트 색인(현재는 메타 링크만)
- 자동 주기 갱신(스케줄러), git 커밋 자동화
- upstream push / 별도 admrule 저장소 분리
