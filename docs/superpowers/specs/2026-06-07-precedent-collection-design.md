# 판례(대법원) 수집·저장·검색 설계

- 상태: 승인 대기 → 구현 계획 단계로 전환
- 작성일: 2026-06-07
- 범위: 대한민국 **대법원 판례 전량**을 OpenAPI에서 수집하여 Git 마크다운으로 저장하고, 기존 Typesense 검색에 통합한다.

## 1. 배경 / 목표

현재 `law.zihado.com` 저장소는 법령(`kr/`)을 마크다운 + Git(개정마다 공포일자 커밋)으로 관리하고,
`search/`의 Typesense 인덱서(조문 단위) + collector + React UI로 초고속 검색을 제공한다.

본 설계는 여기에 **판례(case law)** 를 추가한다.

핵심 결정:

1. **수집 범위**: 대법원 판례 전량 (`org=400201`). 가장 영향력 크고 규모 관리가 가능.
2. **저장 위치**: 같은 repo의 `prec/` 디렉터리 신설.
3. **검색 통합**: 별도 Typesense 컬렉션(`precedents`) + 통합 UI(법령/판례 탭 전환).
4. **운영**: 서버 cron/CI로 신규 판례만 증분 수집(불변 일련번호 resume).

법령과의 결정적 차이: **판례는 개정되지 않는 불변 문서**다. 따라서 법령의 "개정 히스토리" 대신
**1 판례 = 1 커밋(선고일자, 불변)** 모델을 쓴다.

## 2. 데이터 출처 (OpenAPI)

- 목록: `http://www.law.go.kr/DRF/lawSearch.do?target=prec`
  - 파라미터: `OC`(인증키), `type=JSON`, `org=400201`(대법원), `display`(최대 100), `page`,
    선택적으로 `search`(1=사건명/2=전문), `query`, `prncYd`(선고일자 범위), `JO`(참조법령), `sort`
  - 반환(각 건): 판례일련번호, 사건명, 사건번호, 선고일자, 법원명, 법원종류코드,
    사건종류명, 사건종류코드, 판결유형, 판시여부, 데이터출처, 상세링크
- 본문: `http://www.law.go.kr/DRF/lawService.do?target=prec&ID={판례일련번호}&type=JSON`
  - 반환: 위 메타 + **판시사항, 판결요지, 참조조문, 참조판례, 판례내용(전문)**
- 인증키 `OC`는 기존 `.env`의 `LAW_GO_KR_OC` 재사용.

## 3. 디렉터리 & 파일 구조

```
prec/
  {선고연도}/
    {사건번호}({판례일련번호}).md
```

- 예: `prec/2024/2023다12345(228541).md`
- **연도 샤딩**: 대법원 판례 수만 건 → 한 디렉터리 폭발 방지, `git log`·탐색 성능 확보.
- **사건번호**(사람용) + **판례일련번호**(API 고유키): 사건번호는 연도/법원 간 전역 고유가 아닐 수 있어
  일련번호를 괄호로 병기해 충돌을 해소한다. 법령의 `파일명(법령구분).md` 충돌 규칙과 동일 철학.
- 파일명에 쓸 수 없는 문자(`/` 등)는 법령 디렉터리 규칙과 동일하게 정규화/제거한다.
- Unicode 정규화: 법령과 동일하게 가운뎃점 `·`(U+00B7) → `ㆍ`(U+318D).

## 5. Git 커밋 모델

- **한 번의 수집 = 한 커밋** (배치). 7만여 건을 파일마다 커밋하면 history가
  비대해지고 느리므로, 한 수집 실행에서 새로 추가된 판례 전체를 단일 커밋으로 묶는다.
- **불변**: 판례는 개정되지 않으므로 수정 커밋이 없다(추가만). 일일 증분도 그 날 신규분을 1커밋.
- **날짜의 진실은 frontmatter**: 선고일자·사건번호 등은 각 파일 frontmatter가 원천이므로
  커밋 author date를 선고일자로 분리하지 않는다(법령 repo와 다른 점 — 판례는 대량·불변이라 배치가 합리적).
- 커밋 메시지:

  ```
  판례: 대법원 판례 75000건 추가

  선고일자·사건번호 등 메타는 각 파일 frontmatter 를 참조하세요.
  출처: 국가법령정보센터 OpenAPI (https://open.law.go.kr)
  ```

## 6. 수집기 (`search/collector_prec/`)

기존 `search/collector/`(행정규칙 수집기) 패턴을 복제·재사용한다. 모듈 구성:

- `config.py`: `LAW_GO_KR_OC` 재사용, `PREC_ROOT=../prec`, `concurrency`, `retry`.
- `client.py`: 목록 페이징(`lawSearch.do target=prec org=400201`) + 본문 조회(`lawService.do ID=일련번호`).
- `convert.py`: API JSON → frontmatter + 본문 마크다운(순수 함수, 단위 테스트 대상).
- `write.py`: 경로 결정(연도/사건번호/일련번호) + 원자적 쓰기. 동일 일련번호 충돌 시 스킵.
- `fetch.py`: 오케스트레이션.

동작 흐름:

1. 목록 페이징으로 (판례일련번호, 사건명, 사건번호, 선고일자 …) 메타 수집.
2. **resume(불변)**: 목적 경로에 해당 **판례일련번호** 파일이 이미 있으면 본문 조회 없이 스킵 → 증분.
3. 신규 건만 본문 조회 → convert → 원자적 write.
4. 한 건 실패는 격리(`skip|write|empty|fail`)하여 전체를 막지 않음. 네트워크 호출은 락 밖 병렬.

CLI:

```bash
python -m collector_prec.fetch            # 전량(신규만)
python -m collector_prec.fetch --limit 5  # 스모크 테스트
```

## 7. 인덱서 (`search/indexer/` 확장)

- **별도 컬렉션** `precedents`. 도큐먼트 = 판례 1건(법령처럼 조문 분할하지 않음).
- 파서 신설: `prec/**/*.md` → frontmatter + 섹션(판시사항/판결요지/참조조문/참조판례/판례내용).
  법령 조문 파서(`parse.py`)와 분리된 `parse_prec.py`로 둔다.
- 스키마 필드(요지): `precedent_id`, `case_name`, `case_no`, `court`, `case_type`,
  `judgment_type`, `decided_date`(int64, 정렬/필터), `decided_year`(facet),
  `holding`(판시사항), `summary`(판결요지), `body`(판례내용), `refs_article`(참조조문), `url`.
- 질의 가중치: `case_name(5) · holding(4) · summary(4) · body(2) · refs_article(1)`.
- 패싯: `court · case_type · decided_year · judgment_type`.
- 인덱싱 CLI는 법령과 동일 패턴: 전량 재생성 / `--keep` 증분 upsert.

## 8. UI (`search/ui/` 확장)

- 상단 **법령 / 판례 토글 탭**. 탭에 따라 Typesense 어댑터의 대상 컬렉션(`laws`↔`precedents`) 전환.
- `PrecedentHitCard`: 사건명 · 법원 · 선고일자 · 사건번호 · 판시사항 하이라이트.
- 판례 전용 패싯 사이드바(법원/사건종류/선고연도/판결유형).
- URL 동기화(routing)에 활성 탭 상태 포함 → 링크 공유 시 탭 유지.
- 커맨드 팔레트(⌘K)는 현재 탭의 컬렉션을 대상으로 검색.

## 9. 운영 / 자동화

- **초기 적재(back-fill)**: 로컬에서 `collector_prec.fetch` 1회 전량 실행 후 일괄 커밋.
- **증분 운영**: 서버 cron 또는 GitHub Actions로 매일 → 신규 대법원 판례만 증분 수집 →
  선고일자 author date로 자동 커밋 → 선택적으로 인덱스 증분 upsert(`--keep`).
- 인증키/시크릿은 환경변수/CI 시크릿으로 주입(하드코딩 금지).

## 10. 비목표 (YAGNI)

- 하급심(`400202`) 판례 수집 — 1차 범위 제외(추후 `org` 파라미터만 확장하면 됨).
- 판례 간 인용 그래프, 법령↔판례 양방향 자동 링크 — 후속 단계.
- 판례 요약/키워드 자동 생성(MCP `summarize_precedent` 등) — 후속 단계.

## 11. 테스트 전략

- `convert.py`: API JSON fixture → 기대 마크다운(frontmatter/섹션/정규화/빈 섹션) 단위 테스트.
- `write.py`: 경로 결정(연도 샤딩, 사건번호 정규화, 일련번호 충돌 스킵) 단위 테스트.
- `parse_prec.py`: 마크다운 → 도큐먼트 필드 매핑 단위 테스트.
- resume 동작: 동일 일련번호 존재 시 스킵 검증.
- 인덱싱/검색 스모크: 샘플 판례 색인 후 사건명·판시사항 질의 매칭 확인.
